--------------------------------------------------------------------------------
1. VISÃO DO PROJETO
--------------------------------------------------------------------------------
A Low Prices é uma plataforma que liga clientes a profissionais para pequenos
serviços locais (canalizador, eletricista, pintor, jardineiro, limpeza,
mudanças, montagem de móveis, informática, reparações).

Objetivo: qualquer pessoa consegue pedir um serviço em menos de 2 minutos;
qualquer profissional consegue aceitar um trabalho em menos de 1 minuto.

Documentação completa em docs/ (ver secção 4).

--------------------------------------------------------------------------------
2. ARQUITETURA
--------------------------------------------------------------------------------
Ver docs/architecture/MONOREPO_ARCHITECTURE.md para o documento de referência
completo (estrutura de pastas, responsabilidades, comunicação entre apps,
convenções, scripts).

Resumo: Monólito modular (NestJS) com Clean Architecture, Feature-Based
Architecture, SOLID, Repository Pattern e Dependency Injection em todas as
camadas (backend, web, mobile). Uma única API, uma única base de dados.

7. DECISÕES TÉCNICAS TOMADAS (e porquê)
--------------------------------------------------------------------------------
- (Fases anteriores) Monólito modular; Result Pattern no mobile; autosave
  nativo por plataforma; categorias centralizadas por ficheiro; Firebase/
  Maps só como contratos até haver credenciais; PlaceholderPage no mobile.
- Refresh token OPACO (string aleatória), não um JWT — não precisa de ser
  autocontido porque o servidor consulta sempre a BD para o validar; ser
  opaco reduz superfície de ataque.
- Refresh token do Website em cookie httpOnly + também devolvido no body
  da resposta (para o Mobile o guardar em secure storage) — o Website
  ignora esse campo do body por design.
- Rotação de refresh token com deteção de reuso: token já substituído
  sendo reutilizado é sinal de roubo → revoga todas as sessões do
  utilizador imediatamente.
- Eliminação de conta é sempre soft-delete (nunca apagar fisicamente) —
  mantém integridade referencial e cumpre RGPD via anonimização do email.
- Documentação centralizada em docs/, nunca solta na raiz (decisão da
  Fase 5, após feedback explícito).
- Dashboards: só 2 páginas de referência totalmente construídas (Home +
  "Os meus pedidos"); as restantes 18 usam StubSection/DashboardTabStub
  com navegação real — decisão deliberada para não gastar esforço em UI
  detalhada antes de existir schema/endpoint para os dados reais (Fases
  9-13). Documentado, não escondido.
- "Estado dos pedidos" e "Calendário" não são rotas de navegação à parte
  — ficam dentro de "Os meus pedidos"/"Pedidos disponíveis" e "Agenda"
  respetivamente, como visualizações da mesma informação.
- Chat, Agenda e Avaliações desenhados desde já com modelos Prisma
  completos (mesmo sem implementação) para a Fase 8-13 não exigir
  redesenho de schema — só ligar os endpoints.

10. PROBLEMAS ENCONTRADOS E SOLUÇÕES APLICADAS
--------------------------------------------------------------------------------

ficheiro / conversas anteriores — resumo: dark mode por defeito indevido,

NOVO NESTA FASE — CORRUPÇÃO ESTRUTURAL DO MONOREPO:
Auditoria completa revelou que package.json (raiz), package.json
(apps/api), .env.example (raiz) e .gitignore (raiz) tinham sido
sobrescritos com cópias do conteúdo de apps/web (provavelmente durante uma
fusão de zips anterior descuidada). Consequência: o package.json REAL do
backend NestJS (com @nestjs/common, Prisma, etc.) tinha desaparecido por
completo. Corrigido nesta fase:
- package.json raiz: restaurado para o conteúdo genérico do Turborepo
- apps/api/package.json: recriado com todas as dependências (Fase 1 +
  Fase 5: @nestjs/jwt, @nestjs/passport, passport-jwt, @nestjs/throttler,
  argon2, helmet, cookie-parser, class-validator, class-transformer)
- .env.example raiz: restaurado para as variáveis do backend/infra
- .gitignore raiz: restaurado para o conteúdo genérico do monorepo
Lição aplicada: o campo "name" de cada package.json identifica
inequivocamente a que pasta pertence — verificar sempre esse campo ao
investigar problemas de dependências estranhos.

  ver STORAGE_ARCHITECTURE.md, continua só arquitetura
- Extensão do matching por disponibilidade/documentos validados —
  precisa do módulo Agenda (Fase 10) e de perfis com documentos
  aprovados a sério, não só o schema
- Auditoria de responsividade a 9 breakpoints — precisa de inspeção
  visual real, que não consigo fazer sem acesso ao ecrã do utilizador
- Evolução do Design System e auditoria de performance — adiadas para
  não diluir esforço a meio de tantas frentes ao mesmo tempo
